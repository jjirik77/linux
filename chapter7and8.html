Physical Storage Layers

In Linux, storage is organized strictly from physical electronics up to directory tree endpoints:

  • Raw Block Device: Hardware drives (e.g., SATA /dev/sda, NVMe /dev/nvme0n1, VirtIO /dev/vda).
  • Partition: Logical slices on the disk (e.g., /dev/sda1, NVMe /dev/nvme0n1p1).
  • Filesystem: The indexing format (e.g., ext4, xfs, btrfs).
  • Mount Point: The target directory where the filesystem attaches (e.g., /, /home, /var).
Why this matters: Linux doesn't use drive letters like C: or D:. Everything exists in a single unified directory tree starting at /. Isolating paths like /var onto separate partitions protects the root OS from running out of space due to rogue logs.

Inspection Commands & Quiz

Key tools administrators use to inspect block devices before mounting:

  • lsblk: Lists block devices in a visual parent-child hierarchy tree.
  • blkid: Prints UUIDs and filesystem TYPE attributes.
  • fdisk -l: Displays low-level sector geometry and partition tables.

Master Boot Record (MBR) vs. GUID Partition Table (GPT)

CompTIA Linux+ heavily tests the structural specifications and limitations of both partition table schemes:

Specification MBR (Legacy BIOS) GPT (Modern UEFI)
Maximum Disk Size 2 Terabytes (2 TB) (32-bit sector addressing) 9.4 Zettabytes (9.4 ZB) (64-bit LBA addressing)
Partition Maximum 4 Primary partitions (or 3 Primary + 1 Extended containing logical partitions) 128 Partitions by default in Linux
Redundancy & Headers Single sector (LBA 0, first 512 bytes). No backup. Corrupted sector 0 = lost partition table. Primary GPT at LBA 1 and a Secondary Backup GPT stored at the very last sectors of the disk.
Integrity Protection None CRC32 Checksums verify header and partition table health.

Partitioning CLI Utilities

  • fdisk: The standard menu-driven tool (historically MBR; modern versions support GPT). Core keys: m (menu), p (print table), n (new), d (delete), t (type code), w (write to disk), q (quit without saving).
  • gdisk: GPT-dedicated interactive tool. Uses 4-digit hex codes (e.g., 8300 Linux FS, 8200 Linux Swap, EF00 EFI System).
  • parted: Non-interactive/scriptable CLI tool capable of handling disks > 2TB (mklabel gpt, mkpart, resizepart).

The 6-Field Anatomy of /etc/fstab

The /etc/fstab configuration file controls automatic filesystem mounting during system boot. Every active entry requires exactly 6 space-delimited positional fields:

cat /etc/fstab 
# <file system>                           <mount point>   <type>  <options>       <dump>  <pass>
UUID=3a7b9c12-4d5e-6f7a-8b9c-0d1e2f3a4b5c  /var            xfs     defaults,noatime 0       2
  1. Device Identifier: Preferred: UUID=... (immune to drive cable order changes). Also accepts /dev/sdX or device labels.
  2. Mount Point: Target directory in the tree (e.g., /, /home, /data, or none for swap).
  3. Filesystem Type: ext4, xfs, btrfs, vfat, or swap.
  4. Mount Options: defaults (rw, suid, dev, exec, auto, nouser, async), plus ro, noexec, usrquota, nofail.
  5. Dump Flag: 0 = ignore during backup; 1 = back up with legacy dump utility. (Almost always 0 on modern servers).
  6. Fsck Pass Order: Boot filesystem check order: 0 = do not check (used for swap and XFS); 1 = root partition /; 2 = all other local drives checked sequentially.
Exam Tip: Always test changes to /etc/fstab using mount -a before rebooting! If there is a syntax error, mount -a will report it immediately; otherwise, the system will halt into Emergency Mode during boot.

Inodes & The "No Space" Paradox

Every file on an ext4 or XFS filesystem requires two things: data blocks (holding file content) and an inode (index node holding metadata: permissions, owner, timestamps, and block pointers).

The Inode Exhaustion Trap: If an application creates millions of empty (0-byte) temporary or log files, the disk can run out of inodes while having hundreds of gigabytes of free disk space. Any new file creation fails with: No space left on device.
  • df -h: Shows disk block capacity in human-readable gigabytes.
  • df -i: Shows disk inode usage and percentage remaining.
  • du -sh /path/*: Summarizes folder block consumption to find giant directories.

Disk Quotas & LUKS Encryption

Disk Quotas: Prevent individual users or groups from filling shared drives.

  • Soft Limit: Warning threshold. Users can temporarily write above this limit during a grace period (default: 7 days).
  • Hard Limit: Absolute ceiling. Further write attempts are blocked immediately.
  • Tools: quotacheck -cugm, quotaon -v /home, edquota -u <user>, repquota -a.

LUKS (Linux Unified Key Setup):

The standard specification for full-disk and partition encryption. Workflow: cryptsetup luksFormat /dev/sdb1 → cryptsetup open /dev/sdb1 secure_vault → formats virtual device /dev/mapper/secure_vault → mounts to directory.

Logical Volume Management (LVM)

LVM introduces an abstraction layer between physical hardware and mounted filesystems, enabling dynamic resizing without downtime.

The LVM Three-Tier Hierarchy:

  • 1. Physical Volume (PV): Raw disks or partitions initialized for LVM via pvcreate /dev/sdb.
  • 2. Volume Group (VG): The shared storage pool combining one or more PVs via vgcreate vg_data /dev/sdb /dev/sdc.
  • 3. Logical Volume (LV): Virtual partitions carved out of the VG pool via lvcreate -L 50G -n lv_var vg_data. Filesystems are formatted on /dev/vg_data/lv_var.
Why this matters: If a database running on an LV runs out of space, the admin simply executes lvextend -L +20G -r /dev/vg_data/lv_db. The -r flag expands the underlying filesystem online instantly with zero downtime.

RAID Architecture Fundamentals

RAID 0 (Striping): Performance focus. Data split across 2+ drives. No redundancy. If 1 disk fails, 100% of data is lost.

RAID 1 (Mirroring): High reliability. Exact replica across 2 drives. 50% capacity efficiency. Survives 1 drive failure.

RAID 5 (Distributed Parity): Balanced. Requires 3+ drives. Capacity = (N - 1). Survives 1 drive failure through XOR parity reconstruction.

RAID 10 (Striped Mirrors): Combines speed of RAID 0 with safety of RAID 1. Requires 4+ drives (even count). 50% capacity. Can survive multiple disk failures if in different mirror sets.

LVM vs RAID: RAID provides hardware fault tolerance (protecting against disk death). LVM provides storage flexibility (space allocation and expansion). Enterprise servers frequently build LVM Volume Groups on top of hardware RAID arrays!
