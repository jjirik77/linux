Virtualization Fundamentals

Virtualization abstracts physical hardware to create virtual representations of servers, storage, and networks. The core component is the Hypervisor (or Virtual Machine Monitor - VMM), a concept originally developed by IBM.

Linux+ Exam Focus

Be able to clearly distinguish between Type 1 and Type 2 hypervisors, and recognize common VM file formats (OVF, OVA, VMDK, VDI).

Storage Provisioning

  • Thick Provisioning: Allocates all required disk space upfront. Faster performance, but wastes space if unused.
  • Thin Provisioning: Allocates space dynamically as the VM writes data. Saves storage space but incurs slight overhead as it expands.

File Formats

  • OVF: Open Virtualization Format. A directory with multiple config/disk files.
  • OVA: An archive (tar) of an OVF directory (single file).
  • VMDK: Disk format developed by VMware (used by QEMU/VirtualBox).
  • VDI: Native VirtualBox disk image format.

VM Networking & Management

Linux systems often use libvirt as an abstraction layer to interact with hypervisors (like KVM). The primary command-line tool is virsh (e.g., virsh list --all, virsh start vm1).

Essential virsh Commands (Exam Scope)

virsh list --all # Lists all VMs (running and stopped) on the host.
virsh start vm1 # Boots up a stopped virtual machine named 'vm1'.
virsh suspend vm1 # Pauses a running VM, keeping its state in memory.
virsh migrate --live vm1 qemu+ssh://host2/system # Moves a running VM to another hypervisor ('host2') without downtime.

Virtual Network Modes

Advanced Concepts

Dual-Homed & Bonding

A VM with two NICs is dual-homed. Bonding combines multiple physical/virtual NICs (e.g., enp0s1, enp0s2) into a single logical interface (bond0) for redundancy or increased throughput.

Virtual Switch (vSwitch)

A software construct within the hypervisor that connects virtual NICs (vNICs) of VMs together, functioning exactly like a physical layer-2 switch.

BLOB Storage Concepts

Cloud providers use BLOB (Binary Large Object) storage for unstructured data accessible via HTTP(S). Understanding the types is crucial for selecting the right architecture.

BLOB Type Characteristics Ideal Use Case
Block BLOB Max 100MB/block, up to 50k blocks. Requires a 'commit'. Uncommitted data expires (~1 week). Streaming media, document storage.
Append BLOB Data added to the end only. Existing blocks cannot be modified or deleted. Log files, auditing trails.
Page BLOB 512-byte pages. Optimized for random read/write operations. Up to ~8TB. Virtual Machine disks (VHDs), databases.

Shared Host OS & Kernel

Containers virtualize the OS. They share the host's kernel, making them lightweight, fast to start, and highly efficient. Ideally, one main process runs per container.

Kubernetes (K8s) Vocabulary

Pod

Smallest deployable unit. Contains one or more containers sharing network/storage. Ideally 1 primary container.

Sidecar Container

A helper container attached to a pod to assist the primary container (e.g., logging, syncing files).

Ambassador

A container providing helper services external to the container (e.g., proxying database connections).

Deployment

Manages replicas of pods. Starts, stops, monitors, and restarts them to maintain desired state.

Cluster & Node

A pool of resources. Nodes are individual machines (VM or bare-metal) running deployments.

Persistent Volume

Storage that survives container deletion. Like attaching an external drive to a cluster for stateful data.

Essential kubectl Commands (Exam Scope)

kubectl get nodes # Lists all worker nodes in your Kubernetes cluster.
kubectl get pods # Displays all running pods in the current namespace.
kubectl describe pod <pod-name> # Shows detailed configuration and event history for a specific pod (great for troubleshooting).
kubectl apply -f config.yaml # Deploys or updates resources defined in a YAML configuration file.

Managing Containers: Docker & Podman

For the Linux+ exam, docker and podman commands are essentially interchangeable. Podman is daemonless and rootless by default, preferred in modern Red Hat environments.

Container Execution & Networking Syntax

Before running our first container, let's break down three critical flags you will see repeatedly on the exam:

-p (Port Mapping)

Syntax: -p HostPort:ContainerPort (e.g., -p 8080:80).
Analogy: Think of the host machine as a hotel and the container as a guest's room. The -p 8080:80 flag tells the hotel receptionist (the host on port 8080) to forward all calls directly to the guest's room extension (the container on port 80).

-i (Interactive)

Keeps STDIN (standard input) open even if not attached. It allows you to actually send commands into the container.

-t (Pseudo-TTY)

Allocates a terminal interface. Often combined with -i as -it to give you a fully interactive command-line shell inside the container.

Crucial Exam Concept: Persistent Volumes

By default, data written inside a container is lost when the container is removed. To save data, you must map a host directory to a container directory.

docker run -d -v /media/mydata:/mnt/data nginx

Data written to /mnt/data inside the container actually lives in /media/mydata on the host system.

Automation: Kickstart & Cloud-init

Kickstart (Anaconda)

Automates Red Hat-class OS installations. The installer is called Anaconda.

  • /root/anaconda-ks.cfg: Created automatically after a manual install.
  • To reuse: copy to /root/ks.cfg, modify, and point installer to it using boot parameter inst.ks=
  • system-config-kickstart: GUI tool to edit configs.
  • ksvalidator: Checks syntax before deploying.

Exam Focus: Network Boot Parameters

For automated network installations (PXE), you must pass specific parameters to the kernel at boot so it can reach the network to download the kickstart file:

  • ip= (e.g., ip=dhcp) Configures the network interface.
  • inst.repo= Points to the installation source packages (HTTP/FTP).

cloud-init

The industry standard method for cross-platform cloud instance initialization.

  • Handles tasks on first boot: adding SSH keys, setting hostname, creating users, updating packages.
  • Main configuration file (Memorize this path):
/etc/cloud/cloud.cfg
